## What remains

The implementation is complete; the remaining work is **activation and observation**, not code:

1. **Runtime conformance** — `claude /plugin marketplace add ./` followed by `claude /plugin install <name>@cortex` for each plugin. Re-running `./platform/conformance/conformance produce-verdict plugins/<name>` after install converts each `verdict: incomplete` → `verdict: pass`.
2. **60-day observation window** (Phase 6) — calendar time. The `aggregate-feedback.sh` cron runs weekly; the gate to declare MVP1 stable per `GOVERNANCE.md` §4.7 is purely time + symptom-count.
3. **Per-plugin 30-day observation** (Phase 7) — once installed and exercised, each P1 plugin clears its own 30-day window before being declared admitted-and-stable.
4. **TypeScript hook host** — `PLAN.md §2.2` defers this to a post-MVP1 phase. POSIX shell hooks remain the documented MVP1 fallback. Implement when the team is ready to migrate.
5. **Per-host conformance runners** — `--agent=claude|copilot-cli|codex-cli` flags now live on `conformance-run-golden.sh`, `conformance-run-adversarial.sh`, and `conformance-produce-verdict.sh`. Each runner resolves the host CLI binary (`claude`, `gh-copilot`, `codex`), routes the prompt through the host-specific invocation shape, and binds the `agent` identity into the signed verdict envelope. Verdicts are addressed per-agent (ref `verdict_<plugin>_<version>_<agent>`); the `claude` agent additionally writes the unsuffixed reference for backward compatibility.
6. **Optional Phase 10+ extensions** documented in `PLUGIN-SPECS.md`: language skillsets (`lang-python`, `lang-typescript`, `lang-dotnet`, …) and framework/tool skillsets (`framework-react`, `infra-kubernetes`, …) per the competing-providers rule. **Live examples shipped:** `lang-python`, `lang-typescript`, `lang-dotnet`, `infra-kubernetes`.

## 0. Overview & Objectives

We are building an internal, single-org **Claude Code marketplace** that ships an "AI agent team" — a coherent set of plugins covering the full SDLC. The end state of MVP1 is:

- A marketplace catalog (`.claude-plugin/marketplace.json`) loaded into Claude Code.
- **Five Plugin Packages** installed (`engineering`, `quality`, `platform`, `marketplace`, `methodology`).
- A working end-to-end demo: `/implement` → code authored → unit tests written + run by `quality` → reviewed → built → audited, all with `ArtifactEnvelope`-backed handoffs and a non-bypassable telemetry trail.
- A conformance harness gating plugin admission (CI / publish time, never per-edit) and a feedback loop captured in `PluginFeedback@v1` artifacts.
- A workflow catalog of ~8 reusable scenarios shipped inside the `marketplace` plugin.

### 2.2 Conventions

- **POSIX shell for MVP0–MVP1 hook scripts** (`#!/usr/bin/env bash`, `set -euo pipefail`). The platform plugin will ship a typed Node/TypeScript hook host in a post-MVP1 phase; POSIX shell remains a fallback contract after that. Non-default languages must be declared in `.agent-team/contract.json` and verified by conformance CI.
- **JSON on stdin, JSON on stdout** for all hook scripts. Exit 0 = proceed; non-zero = block (PreToolUse) or warn (PostToolUse). Hook scripts must complete inside the perf budget in `ARCHITECTURE.md` §11.8 (≤ 80 ms p95 for shell-only PreToolUse).
- **Semver per plugin.** No "pillar versioning."
- **No marketing language** in Skill Frontmatter Contract descriptions. Each must contain `Use when:`, `Do NOT use when:`, `Inputs:`, `Outputs:`. The `references_skills:` YAML field is **not** part of the contract — methodology references live in the skill body and are validated by conformance (per `ARCHITECTURE.md` §6.12).
- **State substrate ownership** per `ARCHITECTURE.md` §10.0 — per-path single-writer rule. Composite artifacts merge from per-bundle contributor subdirs; the orchestrator does the merge.
- **Subagents do not nest** (`ARCHITECTURE.md` §6.13). Methodology composition is inline; cross-capability dispatch is one level deep.
- **Plain-prose announcements** are encouraged; structured `TelemetryEvent` is the machine record. Conformance fixtures assert against telemetry, never chat text.

### 2.3 Workflow templates live inside the consuming plugin

Claude Code installs a plugin by copying the plugin directory into its cache. **Files outside the plugin directory do not exist after install.** That means workflow templates have to live inside the plugin that loads them.

For MVP1 all workflow YAML lives at `plugins/marketplace/workflows/`. The `workflow-router` subagent shipped in the `marketplace` plugin resolves workflow ids against `${CLAUDE_PLUGIN_ROOT}/workflows/` — never against the marketplace-repo root. This is enforced by conformance: a workflow-loading skill that resolves outside the plugin tree fails admission.

Plugins other than `marketplace` MAY ship their own workflow templates under their own `plugins/<name>/workflows/` if they declare a custom workflow ID space. P1+.

### 4.6 Deliverable: Hook — `hooks/scripts/route-to-review.sh`

```bash
#!/usr/bin/env bash
set -euo pipefail

# POSIX-shell hook. stdin = JSON, stdout = JSON.
# Triggered by PostToolUse on `Bash:git push`.

input="$(cat)"
matcher_captures=$(echo "$input" | jq -r '.matcher_captures')
ic_id=$(echo "$input" | jq -r '.invocation_context.invocation_id')

# Detect: did this push create a new PR branch?
branch=$(git rev-parse --abbrev-ref HEAD)
if [[ "$branch" =~ ^(feat|fix|refactor)/ ]]; then
  # Write a marker so /review can find this PR
  mkdir -p .agents/state/markers
  echo "{\"pr_branch\": \"$branch\", \"invocation_context_id\": \"$ic_id\"}" \
    > .agents/state/markers/last-push.json

  # Emit telemetry
  echo "{\"event\":\"pr.pushed\",\"branch\":\"$branch\"}" >&2

  echo '{"action":"proceed","message":"Push routed; /review will find it."}'
else
  echo '{"action":"proceed"}'
fi
```

### 5.2 Build: Content-Addressable Store (CAS)

`platform/cas/cas.sh`:

```bash
#!/usr/bin/env bash
# cas.sh — write/read content-addressed artifacts
# Usage:
#   cas.sh put <file>      -> prints SHA-256 id
#   cas.sh get <id>        -> writes content to stdout
#   cas.sh resolve <ref>   -> resolve mutable reference

set -euo pipefail
CAS_ROOT="${CAS_ROOT:-$HOME/.claude-plugin/cas}"
mkdir -p "$CAS_ROOT/objects" "$CAS_ROOT/refs"

case "$1" in
  put)
    id=$(sha256sum "$2" | awk '{print $1}')
    cp "$2" "$CAS_ROOT/objects/$id"
    echo "$id"
    ;;
  get)
    cat "$CAS_ROOT/objects/$2"
    ;;
  put-ref)
    # cas.sh put-ref <name> <id>; writes versioned reference
    echo "$3" > "$CAS_ROOT/refs/$2"
    ;;
  resolve)
    cat "$CAS_ROOT/refs/$2"
    ;;
esac
```

### 5.8 Build: Permission Broker hook (PEP)

`platform/hooks/permission-pep.sh`:

```bash
#!/usr/bin/env bash
# PreToolUse hook. Reads required permission from contract.json,
# checks the current plugin's risk_tier cap, fails closed on overreach.
set -euo pipefail

input="$(cat)"
plugin_id=$(echo "$input" | jq -r '.invocation_context.plugin_id // ""')
tool=$(echo "$input" | jq -r '.tool_name')
path=$(echo "$input" | jq -r '.tool_input.file_path // ""')

# Workspace-state ownership check: writes under .agents/state/<subdir>/
# must come from the bundle that owns <subdir>.
if [[ "$path" == *".agents/state/"* ]]; then
  subdir=$(echo "$path" | sed -n 's|.*\.agents/state/\([^/]*\)/.*|\1|p')
  expected_owner=$(jq -r ".[\"$subdir\"]" "$AGENT_TEAM_HOME/platform/settings/state-ownership.json")
  contract_path="${AGENT_TEAM_HOME}/plugins/$plugin_id/.agent-team/contract.json"
  if [[ -f "$contract_path" ]]; then
    owns=$(jq -r --arg sd "$subdir" '.bundle_contracts_touched | map(. == ($sd | gsub("-"; "_"))) | any' "$contract_path")
    if [[ "$expected_owner" != "$plugin_id" && "$owns" != "true" ]]; then
      echo "{\"action\":\"block\",\"message\":\"Cross-bundle write: $plugin_id may not write under .agents/state/$subdir\"}"
      exit 1
    fi
  fi
fi

echo '{"action":"proceed"}'
```

### 5.9 Build: Prompt-cache discipline + per-bundle MCP scoping

Per `ARCHITECTURE.md` §11.8, prompt caching is the single biggest performance lever. The platform places cache breakpoints at four fixed positions:

1. The canonical system-prompt prefix (always-loaded methodology master skill + AGENTS.md/CLAUDE.md + repo-level instructions). 1-hour TTL.
2. Tool / MCP-server definitions. 1-hour TTL.
3. The active capability skill body. 5-minute TTL.
4. The conversation prefix. 5-minute TTL.

Plugin authors do not place breakpoints themselves. Conformance fails any plugin that ships a setting that disturbs this layout (e.g., injecting always-loaded content between breakpoint 2 and 3).

Per-bundle MCP scoping: MCP servers default to `alwaysLoad: false`. Heavy connectors (databases, vector stores) only sit in main context when a subagent activates them. Authors who set `alwaysLoad: true` must justify it in `.agent-team/contract.json`; conformance flags any case where a non-trivial MCP server is hot-loaded without justification.

Deliverables:

- `platform/settings/cache-policy.json` — names the four breakpoints and the always-loaded set.
- A conformance check that all MVP1 MCP servers are `alwaysLoad: false` (or carry a justification token).

### 5.10 Build: Token-budget hook + 60% session-level alarm

A platform `PostToolUse` hook tracks total input + output tokens per session (read from the tool-result metadata) and decrements a counter held in `.agents/state/markers/budget.json`. Default ceiling is per-workspace policy (suggested 200K for interactive sessions, 100K for CI). The hook emits a `TelemetryEvent` with `level=warn` at 60% of the ceiling and fails closed (returns `{"action":"block"}` on the *next* tool call) at 100%.

`platform/hooks/budget-track.sh`:

```bash
#!/usr/bin/env bash
set -euo pipefail
input="$(cat)"
state=".agents/state/markers/budget.json"
tokens=$(echo "$input" | jq -r '.tool_result.token_cost // 0')
mkdir -p "$(dirname "$state")"
if [[ ! -f "$state" ]]; then echo '{"used":0,"ceiling":200000}' > "$state"; fi
jq --argjson t "$tokens" '.used += $t' "$state" > "$state.tmp" && mv "$state.tmp" "$state"
used=$(jq -r '.used' "$state")
ceiling=$(jq -r '.ceiling' "$state")
pct=$(( used * 100 / ceiling ))
if [[ "$pct" -ge 100 ]]; then
  echo "{\"action\":\"block\",\"message\":\"Token budget exhausted ($used / $ceiling). Run /reset-budget or raise ceiling.\"}"
  exit 1
elif [[ "$pct" -ge 60 ]]; then
  echo "[cortex] WARN: token budget at ${pct}% ($used / $ceiling)" >&2
fi
echo '{"action":"proceed"}'
```

### 6.2 Build: `validate`

- `claude plugin validate --strict <plugin-dir>` — native plugin.json.
- `ajv validate -s plugin-contract.v1.json -d <plugin-dir>/.agent-team/contract.json`.
- **Skill Frontmatter Contract linter** (~50 lines of Python or shell): parse each SKILL.md, check the `description` contains `Use when:`, `Do NOT use when:`, `Inputs:`, `Outputs:`. Fail if missing.
- **Cross-plugin description-overlap check**: scan all admitted plugins' SKILL.md `Use when` phrases; fail on >70% similarity.

- **MCP `alwaysLoad` justification**: any `alwaysLoad: true` MCP server in the plugin's `.mcp.json` must carry a justification token in `.agent-team/contract.json`.

```markdown
description: |

# brainstorm

You are facilitating a brainstorm. Your job is to expand the option space
before narrowing it, ask "what about X?" prompts to push the user past their
first idea, and remain non-judgmental in the divergence phase.

## Procedure

1. Restate the topic in one sentence so we both confirm what we're exploring.
2. Generate at least 5 distinct options. Distinct = different category, not
   variants of the same idea.
3. For each option, note one strength and one risk.
4. Ask the user to pick a category to deepen, or to add their own.
5. On convergence, summarize the 1–3 top candidates with explicit tradeoffs.
6. **Do NOT** write any authoritative artifact (PRD, ADR, etc.). If the user
   wants one of those, hand off by name to the relevant capability skill.
```


The conformance harness greps the body for `methodology.<name>` tokens and validates each referenced skill is admitted. A `references_skills:` YAML field is **not** added — it would be a non-standard extension that Codex and Copilot would silently ignore, locking the canonical authoring vocabulary outside the open AgentSkills standard.

### 7b.4 Conformance for methodology skills

Author at least 4 golden + 3 adversarial fixtures:

**Golden examples:**

- `brainstorm/golden/feature-name` — input "name for a feature that lets users export their data to CSV"; expect ≥ 5 distinct names with strength/risk notes.
- `plan-work/golden/migrate-db` — input "migrate from Postgres to MySQL"; expect ≤ 5 verifiable steps each with explicit verification.
- `verify/golden/incomplete-fix` — input is a code change that doesn't fully solve the user story; expect `verify` to call this out.

**Adversarial examples:**

- `brainstorm/adversarial/asks-for-prd` — input "brainstorm a PRD for X"; expect brainstorm to refuse and hand off to `product.draft-prd`.
- `brainstorm/adversarial/writes-artifact` — assert `brainstorm` does NOT write under `.agents/state/intakes/` or any authoritative subdir.
- `tdd/adversarial/skip-test` — input asks to implement without test; expect `tdd` to refuse and require the test first.

### 7b.5 Deliverables

- [ ] `plugins/methodology/` scaffolded with 6 skills + 4 slash commands.
- [ ] Frontmatter contracts pass linter (all `type: methodology`, all `produces_authoritative_artifacts: false`, no `references_skills:` field).
- [ ] Conformance harness passes for the methodology plugin.
- [ ] `engineering/skills/propose-pr/SKILL.md` updated with **inline** methodology references in its procedure body (no YAML frontmatter additions).
- [ ] Cross-skill reference validation runs as part of conformance: a grep over each SKILL.md body for `methodology.<name>` tokens; `engineering` fails admission if it references a methodology skill that doesn't exist.
- [ ] `engineering/plugin.json` declares native `dependencies: [{"name": "methodology", "version": "^0.1.0", "source": "cortex"}, ...]`.
- [ ] Plugin admitted to `marketplace.json` and signed.

### 7b.6 Success criteria

- `claude /brainstorm "name for a CSV export feature"` produces ≥ 5 distinct options with strength/risk notes — no artifact written.
- `claude /implement <fixture-id>` triggers `plan-work` and `tdd` mid-flow; telemetry shows the methodology dispatch with `produces_authoritative_artifacts: false`.
- A deliberately-broken methodology skill that tries to write under `.agents/state/intakes/` is blocked by the PEP hook.
- A capability skill referencing a non-existent methodology skill fails conformance.

### 7b.7 What to skip

- Methodology plugin v1.0 ships 6 skills; the remaining 10 (research, self-learn, debug, decompose, estimate, risk-assess, read-code, pair-program, retro, hypothesis-test) land in P1.
- No agents, hooks, MCP servers, or monitors at MVP1 — pure skills + commands keep the surface minimal.
- No per-domain methodology variants in MVP1 (P1+ if needed via competing-providers rule).

## 12. Risks, Traps & What NOT to Build

| Trap | Why we avoid it | What we do instead |
| --- | --- | --- |
| Custom event bus (Kafka/NATS) in MVP0 | Premature; bundles + hooks already communicate via the file system | Use `.agents/state/<subdir>/` + platform hooks |
| Custom workflow engine | Subagent dispatch + state files is the workflow engine for MVP1 | YAML workflow templates loaded by `workflow-router` |
| Custom permission UI | Claude Code's permission prompts already exist | Hook-based PEP + native prompts |
| Reinventing OCI/Sigstore | Heavy and unnecessary for single-org | Native marketplace + trust-authority signing of `ConformanceVerdict` only (full envelope signing is opt-in per artifact class) |
| Cross-workspace tenancy | Single workspace covers MVP1 use | `tenant_id` constant; revisit on second workspace |
| Full HITL matrix in MVP1 | 31 checkpoints is ceremony for week 6 | Enforce only M-tier checkpoints (1, 2, 3, 8, 10, 21, 22, 26) per GOVERNANCE.md §5.2; the remaining 23 ship as configurable, off by default, and turn on as their owning bundles arrive |
| Writing all 35 Bundle Contracts before shipping | Paralysis | Five plugins MVP1, then incremental |
| Mandating chat-text visibility markers | Unenforceable, presentation coupling | Structured `TelemetryEvent`; plain-prose announcements allowed; markers never mandatory |
| Fat plugins (one plugin = many bundles) | Violates ownership | Domain-coherent plugins per packaging table |
| LLM-as-judge in MVP1 conformance | Adds nondeterminism on top of nondeterminism | Structural assertions (string contains, file exists, count comparisons); LLM-as-judge in P1 |
| Skipping conformance for "internal trust" | Slips into prod | All plugins must pass before admission, even first-party |
| **Workflow templates outside the consuming plugin** | Claude Code copies the plugin dir into the install cache; root-level templates won't exist post-install | Ship workflow YAML inside `plugins/marketplace/workflows/`; resolve via `${CLAUDE_PLUGIN_ROOT}` |
| **`references_skills:` YAML frontmatter** | Non-standard extension Codex and Copilot silently ignore; locks the canonical authoring vocabulary | Inline `methodology.<name>` references in skill bodies; conformance grep validates |
| **Subagent nesting / deep dispatch** | Claude Code subagents cannot spawn further subagents; soft-recursive workspace polling is hard to bound | Inline methodology composition; orchestrator → workers is one level deep; bounded ≤5-iteration inner loops |
| **Single-writer-per-*artifact*** (instead of single-writer-per-*path*) | Blocks legitimate composite artifacts like multi-reviewer verdicts | Per-path ownership at `.agents/state/<owner>/<artifact-id>/<contributor>/`; orchestrator merges |
| **Always-on MCP servers in main context** | A 15K-token MCP definition sits in every session whether used or not | `alwaysLoad: false` by default; conformance flags exceptions |
| **POSIX shell as a permanent default** | Cold-start variability + JSON-from-bash fragility hurts at scale | Keep POSIX for MVP1; ship a TypeScript hook host in a post-MVP1 phase (POSIX stays as fallback) |
| **Per-session token blindness** | A single `/release` fan-out can burn through quota in minutes | Token-budget hook with 60% warning, 100% fail-closed; per-session ceilings in workspace settings |
| **Treating performance as an afterthought** | A slow stack is a quietly-abandoned stack | Per-workflow p50/p95 SLOs; cache-policy regression check in conformance |
| **Mandatory full-artifact CAS signing** | Heavy for a single-org dev productivity tool | Signing is opt-in per artifact class; the mandatory floor is content-hashing + provenance DAG. Revisit if cortext.ai becomes the substrate for downstream audited systems (open question, §16) |

## 14. Phase 9 — Multi-Agent Portability: Codex and GitHub Copilot

This phase runs **in parallel** starting from Phase 5 (week 6). It is research + a thin adapter, not a full port.

### 14.1 What changed since the architecture was drafted

Three things have moved fast and matter for portability:

1. **`SKILL.md` is now a cross-agent open standard** (April 2026). The same `SKILL.md` with `name` + `description` frontmatter works across Claude Code, GitHub Copilot (CLI, IDE, cloud agent), OpenAI Codex (app, CLI, IDE), Cursor, and 20+ other agents. Our Skill Frontmatter Contract is **stricter** than the minimum required, which is good — Copilot/Codex will accept it but will not require the extra structure.
2. **MCP is universal.** All three target agents consume MCP servers natively. Our Connector Plane is already vendor-neutral.
3. **Plugin packaging diverges.** Each agent has its own catalog format. The plugin *contents* (skills, MCP servers, subagents) are largely portable; the *packaging* needs an adapter.

### 14.2 Portability matrix

For each primitive, what's portable as-is, what needs an adapter, what doesn't port:

| Primitive | Claude Code | GitHub Copilot | OpenAI Codex | Portability |
| --- | --- | --- | --- | --- |
| Skill (with SKILL.md frontmatter) | `skills/<name>/SKILL.md` | `.github/skills/<name>/SKILL.md` or `.agents/skills/` | `skills/<name>/SKILL.md` | **Portable as-is.** Use `.agents/skills/` neutral path. |
| Subagent | `agents/<name>.md` + `subagent_type` | "Custom Agents" via Plugin System; format differs | "Custom Agents" via `agents/openai.yaml` | **Adapter needed.** Same persona content, different file format. |
| MCP Server (Connector) | `.mcp.json` | MCP server registration via plugin manifest | MCP server registration via plugin manifest | **Portable as-is.** |
| Slash command | `commands/<name>.md` | Plugin System slash commands | Plugin System slash commands | **Mostly portable.** Frontmatter shape differs in optional fields. |
| Hook | `hooks/hooks.json` with PreToolUse / PostToolUse / SessionStart / SessionEnd / SubagentStop | CLI session lifecycle (different event names) | CLI session lifecycle (different event names) | **Least portable.** Each agent has its own event model. |
| LSP Server | `.lsp.json` / `lspServers` | Generally not consumed by Copilot CLI; VS Code Copilot uses its own | Not consumed directly | **Claude-specific in practice.** |
| Monitor | `monitors/monitors.json` | No equivalent | No equivalent | **Claude-specific.** |
| `plugin.json` manifest | `.claude-plugin/plugin.json` | `.copilot-plugin/plugin.yml` (or similar; check current docs) | `agents/openai.yaml` + plugin bundle | **Adapter required.** |
| Marketplace catalog | `.claude-plugin/marketplace.json` | Copilot CLI plugin registry; enterprise-managed plugins | Codex plugin marketplace bundle format | **Adapter required.** |
| `.agent-team/contract.json` sidecar | Our marketplace consumes it | Ignored by Copilot natively | Ignored by Codex natively | **Marketplace-internal; portable because everyone ignores it.** |

### 14.3 Adapter strategy — emit at the boundary, not translate in the middle

The cleanest path is **emit, don't translate**. Direct inspection of `obra/superpowers` confirms the specific shape worth copying:

1. **One canonical skill library, authored in Claude Code tool vocabulary.** Skills live under `plugins/<name>/skills/<skill>/SKILL.md`.
2. **Per-platform translation references co-located with each skill** — `plugins/<name>/skills/<skill>/references/codex-tools.md`, `references/copilot-tools.md`, `references/gemini-tools.md`. Each translation reference is a small Markdown file telling the host how to map our Claude-Code tool names (Read, Edit, Bash, Task) into its native ones.
3. **Hook scripts detect the host at runtime via env var** (`CLAUDE_PLUGIN_ROOT`, `COPILOT_CLI`, `CODEX_CLI`, etc.) and emit native JSON for whichever host is active — no translation layer in the middle, no dual emission to dual-counted fields.
4. **Per-host packaging wrappers** (thin `.claude-plugin/`, `.copilot-plugin/`, `.codex-plugin/` directories) hold only manifest + lifecycle wiring; the skill content underneath is shared.

```text
plugins/engineering/
├── .claude-plugin/plugin.json          # canonical (Claude Code native)
├── .agent-team/contract.json           # canonical sidecar
├── skills/
│   └── review-diff/
│       ├── SKILL.md                    # authored in Claude Code tool vocabulary
│       └── references/
```

Adapter scripts in `platform/adapters/`:

- `to-copilot.sh <plugin-dir> <out-dir>` — emits the Copilot manifest from `plugin.json` + `contract.json`; symlinks SKILL.md files (no transform). Per-host translation references already live next to the skill, so the skill payload is identical across hosts.
- `to-codex.sh <plugin-dir> <out-dir>` — emits the Codex manifest.

Adapters are **lossy emitters**, not bidirectional translators. Drift between agent versions is detected weekly by the conformance harness running per-host (§14.7).

### 14.4 What ports cleanly, what doesn't

**Ports cleanly (no transform):**

- All SKILL.md files (Skill Frontmatter Contract is a strict superset of what Copilot/Codex require).
- All MCP server references.
- All `_capability-contracts/*.md` files (they're documentation; agents may or may not load them, but they don't break anything).
- Hook scripts — but only the *scripts*; the registration mechanism differs.

**Needs adapter:**

- Subagent files (different frontmatter / location per agent).
- Slash command files (frontmatter fields differ).
- Plugin manifest (different format per agent).
- Marketplace catalog (each agent has its own).
- Hook registration (different event names; Copilot CLI's `SessionStart` ≠ Claude Code's `SessionStart` in exact semantics).

**Does not port:**

- LSP server integration (Claude-specific in practice; Copilot has its own LSP plumbing in VS Code).
- Monitors (Claude-specific).
- The `.agent-team/contract.json` sidecar enforcement (other agents ignore it; we enforce it in our marketplace tooling).
- The conformance harness (ours is bash/jq + Claude Code dispatch; running fixtures against Codex/Copilot needs an equivalent dispatch layer per agent — defer to Phase 10 if needed).

### 14.5 Recommended adapter scope for first port

Do not try to port everything at once. First port:

- **One plugin** — `engineering` — to **GitHub Copilot CLI** (Copilot has the closest plugin model to Claude Code's).
- **One skill** — `review-diff` — to **OpenAI Codex** (smallest blast radius for the Codex port).

Validate end-to-end: same fixture, different agent, equivalent output artifacts. Then expand.

### 14.6 Where the canonical design lives

The canonical design stays in our repo. Adapters are **lossy emitters**, not bidirectional translators. If someone modifies a Codex-emitted skill, they modify the canonical SKILL.md and re-emit; we do not import upstream changes from agent-specific packages.

### 14.7 Conformance for multi-agent ports

Each port has its own conformance run:

- `conformance run-golden --agent=claude-code` (default).
- `conformance run-golden --agent=copilot-cli` (Phase 9.5).
- `conformance run-golden --agent=codex-cli` (Phase 9.5).

A plugin is "portable" only if it passes conformance on each target agent. Drift between agent versions is detected weekly.

### 14.9 Phase 9 success criteria

- The adapter scripts are < 200 lines each.
- The portability report identifies the next 5 plugins likely to port cleanly and the 5 that will need significant work (likely the ones heavy on monitors, LSP, or platform-side hooks).

## 16. Open Questions to Resolve Before Phase 7

These are pre-tracked here so they don't surprise the team at scale:

1. **Trust authority key rotation.** When does the marketplace key rotate? Answer before P1.
2. **Cross-workspace artifact sharing.** Per `GOVERNANCE.md` Q3 — opt-in per workspace pair? Required for sharing connector configs across teams.
3. **External LLM provider allowlist.** Per `GOVERNANCE.md` Q9 — Anthropic-only until P1?
4. **Conformance fixture secrecy.** Per `GOVERNANCE.md` Q11 — public golden fixtures, secret holdout? Decide before opening fixtures to plugin authors.
5. **Pluggable model providers via the adapter layer.** If Phase 9 succeeds for one plugin, do we offer GitHub Copilot Models / OpenAI Codex as `Model` primitive bindings? Decide at end of Phase 9.
6. **Is cortext.ai a dev productivity tool or the substrate for downstream audited systems?** The current design assumes the audited-substrate case (signed `ArtifactEnvelope`, full provenance DAG). If we're really shipping a dev productivity tool, drop mandatory signing in favor of content-hashing + provenance; signing becomes opt-in per artifact class (`SecurityFinding`, `ReleaseRecord`). Decision affects MVP1 §1 (key generation), §5.2 (CAS), §6.5 (verdict signing). Default for MVP1: **dev productivity tool**; signing applies only to `ConformanceVerdict`. Re-evaluate at end of Phase 6.
7. **Multi-user workspace isolation.** When two devs share a checkout, how is `.agents/state/<user-id>/` namespacing turned on? Per `ARCHITECTURE.md` §10.0 the flag is `AGENT_TEAM_MULTI_USER=1`; spec the migration path before the first two-person team starts using cortext.ai.
8. **Cancellation + resumability semantics across timeouts.** What happens when an `ApprovalRequest` expires at the SLA before a human responds? Workflow template default in MVP1 = `state: expired`, no auto-approval. Spec the resumption UX for `/resume <workflow-id>` before P1.
9. **Memory / context substrate beyond CAS.** Per `GOVERNANCE.md` Q2 — what backs methodology skills like `research` and `self-learn` that need cross-session memory? Decide before `methodology v1.1` ships in P1.
10. **TypeScript hook host timing.** When does the platform plugin ship `@cortext/hook-host` as the default? Aim for the early part of Phase 7 (alongside `methodology v1.1`) so P1 plugins can use it from day one.
11. **DORA metrics in `release-operate`.** Tying commits to deploys for lead-time and change-failure-rate is non-trivial. Spec the emitter before `release-operate v1.0` lands.
